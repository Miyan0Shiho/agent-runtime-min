# M4 契约:Eval 基础设施(回归集 + Trace 评估 + 判定)

> 状态:设计产物 · 2026-10-12 · 作者:本人
> **上游依据:无。** DSH 源码中不存在 eval 包(`packages/` 下无 `eval`/`bench` 业务包),无 LLM-as-Judge 实现;社区 4,508 个插件中仅约 20 个涉及评估。**本文是原创设计**,证据标记见 §1。
> 前置:[M1 契约](M1-log-as-truth.md)——**评估输入必须从事件日志派生,不另建一套记录**。
> **本文抽掉任何外部项目的名字后必须能独立成立。**

---

## 0. 一句话结论

Eval 的唯一价值是**回答「改动之后是变好还是变坏」**。因此它的设计目标不是「评估得准」,而是**「评估结论可信到可以据此做决定」**。

推论:**不可信的评估比没有评估更糟**——它会让人相信一个错误的结论,并把系统带向错误方向。所以本契约的重心在**如何发现评估本身失效**(§6),而不是如何打出一个分数。

第二条推论:**能从确定性事实判断的,绝不交给模型**。文件是否改了、测试是否过了、命令是否成功——这些用代码判;只有「质量」这类无法确定性判定的,才用模型判。

## 2. 评估输入:从日志派生

### 2.1 唯一输入源

```text
事件日志(M1)
  → 一次运行的 Trace(可重放的完整记录)
  → 评估用例的结果
```

【推导】**评估不另建记录**。理由:若评估有自己的记录,就会出现「日志说 A、评估说 B」的分裂;而 M1 的契约保证日志能重建模型看到的每一个字节,评估需要的一切都在其中。

**可重放性**:同一份日志,重放必须得到同一个评估结果。若不能,说明评估引入了日志之外的状态——那是 bug。

### 2.2 Trace 的三层

| 层 | 内容 | 用途 |
|---|---|---|
| **结果层** | 最终答案 / 改动 / 退出状态 | 通过与否 |
| **过程层** | 工具调用序列、参数、结果、失败 | 为什么失败 |
| **成本层** | token 数、步骤数、耗时 | 效率是否退化 |

【设计】三层分开记录,分开判定。**只看结果层的评估会漏掉「碰巧对了」**;只看过程层会漏掉「绕了远路但做对了」。

## 3. 判定策略:确定性优先

```text
判定(用例) =
  ① 确定性检查(代码)      ← 能判就判,判完即止
  ② 模型判定(judge)        ← 只在 ① 无法判定时使用
```

### 3.1 确定性检查(优先)

| 检查 | 判据 |
|---|---|
| 文件改动 | 目标文件的内容/存在性与预期一致 |
| 测试通过 | 指定命令的退出码为 0 |
| 命令成功 | 指定命令的退出码 |
| 输出匹配 | 正则/子串/JSON 结构匹配 |
| 未越权 | 日志中不存在被禁止的工具调用 |
| 成本上限 | token/步骤数在预算内 |

【设计】**这些检查必须能独立运行**,不依赖模型。理由:它们是评估的**地基**;若地基需要模型,整个评估的可信度就递归地依赖模型。

### 3.2 模型判定(judge)

只在「质量」类维度使用:回答是否切题、解释是否清楚、方案是否合理。

【已知失效模式】judge 有四类系统性偏差,必须在设计上防:

| 偏差 | 表现 | 防护 |
|---|---|---|
| **位置偏差** | 偏好先出现的选项 | A/B 两次运行,交换顺序取一致结论 |
| **冗长偏差** | 偏好更长的回答 | 长度归一化;或把长度作为独立维度单独评 |
| **自我偏好** | 偏好与自己同源的模型输出 | judge 与被评模型**不同源**;或至少记录同源标记 |
| **评分漂移** | 同一输入不同时刻给出不同分 | 固定 judge 版本 + 温度 0;定期用锚点用例校准 |

【设计】**judge 的结论必须带不确定性**。若两次运行(交换顺序)结论不一致,该用例标记为**「判定不可靠」**,而不是取平均。取平均会把「不一致」伪装成「中等」。

## 4. 回归集

### 4.1 结构

```text
case:
  id:          唯一标识
  version:     用例版本(改判据即升版)
  setup:       初始仓库状态(或 fixture 引用)
  input:       给 agent 的任务
  checks:      确定性检查列表
  judge:       可选的模型判定配置
  budget:      token / 步骤 / 时间上限
```

【设计】**用例必须自包含**。依赖外部状态(网络、某个已存在的仓库)的用例会随时间失效,且失效时难以察觉。

### 4.2 冻结

【设计】**回归集一旦用于对比,必须冻结**。改判据 = 新版本;新旧版本的结果**不可直接比较**。

理由:若允许边改判据边对比,「指标上升」可能只是判据变松了——这正是最危险的自欺。

### 4.3 规模

【设计】第一版 **15–25 个用例**,覆盖:

| 类别 | 数量 | 为什么 |
|---|---|---|
| 单文件修改 | 3–5 | 最基本的能力 |
| 跨文件修改 | 3–5 | 需要理解结构 |
| 测试失败定位 | 2–3 | 需要读输出、推理 |
| 重构且行为不变 | 2–3 | 最容易「改坏但测试没覆盖」 |
| 长会话(触发压缩) | 2–3 | **M2 的验收依赖它** |
| 故障恢复 | 2–3 | **M3 的验收依赖它** |
| 权限拒绝后停止 | 1–2 | 安全默认值 |

【推导】后三类不是「顺便加的」——**M2 与 M3 的量化指标没有这些用例就无法测量**。Eval 与 M2/M3 是同一份基础设施的两个方向。

## 5. 判定流程

```text
run(case, candidate) →
  ① 准备:重置到 case.setup 的初始状态
  ② 执行:跑 agent,记录完整日志
  ③ 确定性检查:逐条跑 checks
  ④ 若 ③ 全过且 case 有 judge 配置 → 跑 judge(两次,交换顺序)
  ⑤ 汇总:结果 + 过程 + 成本
  ⑥ 与基线对比
```

**关键约束**:

- 【设计】**每次运行前重置状态**。不重置的评估会在第二次运行起测的是「上一个运行留下的状态」。
- 【设计】**执行与判定分离**。执行阶段不读判据(避免 agent 看到预期答案);判定阶段不重新执行。
- 【推导】**日志必须完整保留**。判定失败时,唯一的排障依据是日志。

## 6. 如何发现评估本身失效

这是本契约最重要的部分。

### 6.1 四类失效与检测

| 失效 | 症状 | 检测方法 |
|---|---|---|
| **判据漂移** | 指标上升但人工抽查变差 | 定期人工抽查 N 个用例,与自动结论对比 |
| **用例腐化** | 用例因环境变化而必然失败/必然通过 | 用**已知正确**的实现跑一遍:应全过;用**已知错误**的实现跑:应全失败 |
| **judge 退化** | 结论趋于一致(全过或全败) | 监控结论分布;方差过低即告警 |
| **不可复现** | 同一输入两次结论不同 | 同一用例连跑 3 次,结论必须一致 |

### 6.2 金丝雀用例

【设计】回归集中保留 **2–3 个「已知答案」的用例**:

- 一个**必然通过**(若它失败,说明评估基础设施坏了,不是被评对象坏了)
- 一个**必然失败**(若它通过,说明判据太松)

【设计】**这两条用例的存在意义不是评估 agent,而是评估评估本身。** 它们必须先于其他用例运行。

### 6.3 人工抽查的触发条件

【设计】不设固定周期,设**触发条件**:

- 自动指标变化超过阈值(例如 ±10%)时,抽查该批次
- 新增/修改用例后,抽查一次
- judge 版本变更后,抽查一次

理由:固定周期会在「什么都没变」时浪费人力,在「变了」时来不及。

## 7. 指标

| 指标 | 定义 | 用途 |
|---|---|---|
| **通过率** | 通过用例数 / 总用例数 | 主指标 |
| **回归检出率** | 注入的已知回归中被检出的比例 | **评估能力的度量**(见 §8) |
| **可复现性** | 连跑 3 次结论一致的用例比例 | 评估可信度 |
| **成本** | token / 步骤 / 时间的分布 | 效率是否退化 |
| **过程质量** | 越权次数、失败恢复次数 | 过程层 |

【设计】**不设单一综合分**。综合分会掩盖「通过率涨了但越权也涨了」这类关键信号。

---

## 8. 评估的自我验证:注入回归

【推导】这是 M4 的量化验收方式,也是本契约能自证的方式:

```text
人为注入 3 个已知回归(例如:让压缩阈值失效、让工具失败不落日志、让配对断裂)
→ 跑回归集
→ 断言:这 3 个回归全部被检出
```

**检出率必须 100%**。若注入的回归检测不出来,说明回归集覆盖不到该机制——**这是回归集的缺陷,不是被评对象的优点**。

## 9. 不变量

| # | 不变量 | 违反了会怎样 |
|---|---|---|
| M4.1 | **评估输入只来自事件日志** | 日志与评估结论分裂 |
| M4.2 | **同一日志重放必须得到同一结论** | 评估不可信 |
| M4.3 | **确定性检查优先**,能代码判的不给模型 | 引入不必要的不可靠性 |
| M4.4 | **judge 必须两次、交换顺序**;不一致标记为「不可靠」而非取平均 | 把不一致伪装成中等 |
| M4.5 | **judge 与被评模型不同源**(或显式记录同源) | 自我偏好偏差 |
| M4.6 | **每次运行前重置状态** | 测的是上一次的残留 |
| M4.7 | **执行与判定分离**;执行阶段不读判据 | agent 看到预期答案 |
| M4.8 | **回归集冻结**;改判据即升版 | 指标上升只是判据变松 |
| M4.9 | **金丝雀用例先于其他用例运行** | 基础设施坏了却去解读业务指标 |
| M4.10 | **不设单一综合分** | 掩盖反向信号 |
| M4.11 | **失败时必须保留完整日志** | 无法排障 |
| M4.12 | **注入回归的检出率必须 100%** | 回归集覆盖不足被误读为质量好 |

## 10. 我们的选择(全部为【设计】)

| 维度 | 选择 | 理由 |
|---|---|---|
| 输入源 | M1 日志 | M4.1;避免双份记录 |
| 判定 | 确定性优先 + judge 兜底 | 可信度最大化 |
| 回归集规模 | 15–25 用例 | 单人可维护;覆盖 M2/M3 验收所需 |
| 冻结策略 | 判据变更即升版 | 防止「指标上升 = 判据变松」 |
| judge 校准 | 交换顺序 + 锚点用例 | 防位置偏差与漂移 |
| 自证方式 | 注入回归,要求 100% 检出 | 可量化,能证伪 |
| 用例格式 | YAML(与仓库同版本管理) | 可读、可 diff、可评审 |

**明确不做**:

- **不建在线评估服务**。第一版是本地命令。
- **不做实时监控看板**。触发条件式抽查(§6.3)替代。
- **不做多 judge 投票**。交换顺序两次已能暴露不一致;投票会把不一致平均掉。

## 12. 未解决 / 待验证

1. ~~**【未验证】15–25 个用例是否足以检出真实回归。**~~ **已验证（2026-10-16）**：**检出率 100%（3/3）**，达到契约要求的门槛——「若不达 100%，先扩用例，不要降低要求」。

   实测（`make bench`）：`M4 regression detection 100.000 %  3/3 injected regressions detected`。

   用例数也已进入契约要求的区间：原本 **10 条**，其中 `long/compaction-trigger`（**契约指明 M2 验收所依赖的那条**）是一个只被测试调用的独立函数，**从未进入套件**——所以套件报 10 条而 `long-session` 只有 1 条。现在 **18 条**，每个类别都在要求的区间内：

   `single-file 3, cross-file 3, test-failure 2, refactor 2, long-session 2, fault-recovery 2, permission 2`

   四条测试固定这个要求（总数、每类区间、压缩用例在套件内、两个机制类别存在），这样将来删掉一类会**失败**而不是悄悄降低覆盖。
2. ~~**【未验证】judge 在本机模型上的偏差幅度。**~~ **已用真实模型实测（2026-10-16，deepseek-chat）**。

   **重复性**：同一份答案跑 10 次，**全部 5.0，标准差 0.00**，10/10 标记可靠。

   **但一个满分答案的零方差什么都说明不了** —— 一个「永远给 5 分」的 judge 也会产生同样的数字。所以补了**区分度**测试：

   | 答案 | 均分 |
   |---|---|
   | 正确且清晰 | 5.00 |
   | 正确但简略 | 4.83 |
   | **错误** | **1.33** |
   | **有 bug（缺 base case）** | **1.33** |
   | **又长又错（856 字符）** | **1.28** |

   **冗长偏置不存在**：把错误答案从 41 字符**填充到 856 字符**，分数**反而略降**。长度没有换来分数。

   > 方法论要点：**「同一答案重复 10 次都一样」和「这个 judge 有区分度」是两件事**，而**从单一答案上它们看起来完全一样**。只测前者会得到一个漂亮的零方差和一个毫无信息量的结论。

   位置偏置的结构性防御（两次不同顺序、要求一致，不一致则标为不可靠）已在实现中，测试断言的是**形状**而不是「偏置出现」—— 要求偏置出现等于在测试一个缺陷。
3. ~~**【未验证】「同一日志重放得到同一结论」在 judge 存在时能否成立。**~~ **已用真实模型实测（2026-10-16，deepseek-chat）**，结论：**能成立，判定缓存不需要**。

   先说清一件事：**基准测试里那条 `M4 reproducibility 100%` 证明不了这个**。它只跑**确定性检查**（`output_matches` / `file_exists`），**全程没有 judge**——所以它 100% 是平凡的，与契约这条问题无关。

   真正测的是 judge：

   | 答案 | 原始分波动 | 取整后的判定 |
   |---|---|---|
   | 正确 | 0.000 | 5 —— 稳定 |
   | 1-indexed（合法） | 0.167 | 5 —— 稳定 |
   | 缺 base case | 0.000 | 1 —— 稳定 |
   | 错 | 0.000 | 2 —— 稳定 |

   **判定 4/4 稳定。** 原始分确实会动（边界答案上出现过 **6 次里 4 个不同分数**），但：

   - 波动幅度 **≤ 0.17 分**，远在契约自己设的 **±1.0「一致」容差之内**；
   - **取整后判定完全不动**——而阈值比较消费的正是判定。

   契约的判定缓存**以「实测发现重放不一致」为条件**，条件未成立，故不引入。

   > **测试写对了才有意义**：我特意选了一个**确实会抖**的边界答案来测。一个从不波动的 judge 会让这条测试**空转**——而空转的测试会给出「已覆盖」的假象。

   **一次我自己的标注错误**：我最初把那个 1-indexed 实现标为「off by one」，并把 judge 给的 5 分当成 judge 判错。**不是**——它返回 `fib(0)=1, fib(5)=8`，是 **1-indexed 的合法约定**，judge 判对了，**是我的标签错了**。测试里已按它的真实面目命名。
4. ~~**【未验证】用例的「自包含」成本。**~~ **已实测（2026-10-16）**：**阈值远未触及**，而且原因是结构性的。

   18 个用例共 **31 个 fixture 文件，合计约 12.5 KiB**，契约的阈值是 **50 MB** —— **低约 4000 倍**。

   原因：fixture 是**写在用例定义里的内联字符串**，不是磁盘上的文件。一个用例的 `setup` 就写在它描述的任务旁边，所以它花的是**源码字节**而不是仓库产物。**这就是这个担心不成立的原因——没有东西会增长。**

   已加测试固定（同时设一条比契约严格得多的上界）。将来若某个用例内嵌了大东西（抓取的日志、二进制），它会失败——那时契约的「按需生成」才是正确答案。
5. ~~**【推断】执行阶段不读判据是否足够。**~~ **已确认属实，并作为已知边界保留（2026-10-16）**。

   契约自己就写了「这不是 M4 能解决的，属于任务设计问题」——**核查后同意**。若工作量目录里本来就有判据（例如测试文件就在工作区里），agent 可以读到它，而**执行阶段无法阻止**这一点（阻止读取会让「修一个失败的测试」这类任务无法完成）。
