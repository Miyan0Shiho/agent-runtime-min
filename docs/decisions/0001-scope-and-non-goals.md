# ADR-0001:项目范围、非目标与 clean-room 约束

- **状态**:已接受
- **日期**:2026-10-07
- **决策者**:本人
- **后续**:第 1 条(机制数量)与第 4 条(降级路径)已被 [ADR-0002](0002-design-alignment-and-native-builtins.md) 修订:机制从 3 扩到 4(新增 M4 Eval),降级路径改为「优先砍 M4」。第 2、3 条继续有效。

## 背景

`agent-runtime-min` 源于对 DeepSeek Harness(DSH)的源码拆解积累([sources/dsh-study](../../../../sources/dsh-study/README.md),基线 `0.2.1-alpha.1`)。

约束条件:

1. 项目owner为 2027 届求职者,当前备考研究生,**2026 年 10–12 月每周可用 1–2 小时**,2027 年 1–2 月才可能集中投入。
2. 目标产出一个 **L3「可展示」**项目(判定标准见 [02-projects README](../../README.md)),用于春招简历与考研复试。
3. 上游 DSH 是一个包含数百个 package 的完整 harness,能力面极广。

## 决策

### 1. 只做三个机制,且必须互相咬合

选择 M1 日志即事实、M2 上下文压力处理、M3 工具执行流水线。三者共同服务于一条叙事主线:

> **M1 是地基;M2 与 M3 都只是「向日志追加正确的事件」。**

**为什么不用「按 DSH 功能地图逐项复刻」的做法**:功能地图([06-feature-map.md](../../../../sources/dsh-study/06-feature-map.md))列出 13 个大类、上百个 package。逐项复刻在 8–16 小时设计预算下注定失败,且产出会是"什么都有一点"的浅层 demo——恰恰是面试中最容易被问倒的形态。**深度来自收敛,不来自覆盖。**

### 2. 反向上游的复杂度:先定契约,再写实现

设计期只产出**主链路图 + 机制契约 + 评测方案**三类文档,不写代码。

**为什么**:契约(接口、事件类型、不变量)的讨论成本低、可在碎片时间完成,且**一旦契约稳定,实现阶段就退化为填坑**,可以集中投入。反过来,若设计期就写代码,碎片化的进度会不断产生半成品分支,反而更慢。

### 3. clean-room:读契约,不抄实现

**明确约束**:可以阅读上游的文档(`docs/`)、类型定义、README,用于理解契约与设计意图;**不复制、不改写、不逐行翻译**上游实现代码。

**为什么**:

- **法律与合规**:上游项目的授权条款不因"我改了几个变量名"而失效。派生作品与独立实现的边界必须由行为划清,而不是由改动量划清。
- **能力背书**:面试官一旦察觉是"扒源码",前面所有技术叙事都会失效。反过来,能说清"我读了它的契约文档,理解它为什么这么设计,然后用完全不同的方式实现"——这是加分项。
- **副产品**:不抄反而逼出真正的理解。凡是抄得来的地方,都是讲不透的地方。

**怎么执行**:设计文档中引用上游时,只引用**文件路径 + 类型/接口名 + 设计意图**,不粘贴实现代码。评审标准:任何一份设计文档,抽掉 DSH 的名字后仍能独立成立。

### 4. 接受范围可以再缩

预置的降级路径:设计期若无法完成 3 份契约文档,**砍 M3,保留 M1 + M2**。

**为什么预先写下来**:求职压力下最容易发生的失败模式是"为了简历好看而保留一个讲不透的机制"。提前把降级方案写成决策,可以让未来的自己少一次自我欺骗。

## 后果

**正面**

- 范围收敛,8–16 小时可完成设计期,存在真实的可完成路径。
- 每个机制都有上游源码依据,技术叙事可追溯到具体文件,而不是"我记得好像是"。
- clean-room 约束使项目在法律与面试两个层面都站得住。

**负面 / 风险**

- M1 + M2 + M3 的完整实现可能超出 2027 年 1–2 月的时间预算 → 用第 4 条降级路径兜底。
- 不做 UI 意味着项目"看起来"不如带界面的项目炫 → 用**量化指标**替代视觉冲击,这也是 L3 的要求。
- 与 DSH 行为不一致可能使部分拆解结论无法直接对比复现 → 这是刻意接受的代价,项目的目标是机制理解,不是兼容性。
