# ADR-0002:「设计对齐」定位与原生内置的准入标准

- **状态**:已接受
- **日期**:2026-10-12
- **决策者**:本人
- **取代/澄清**:[ADR-0001](0001-scope-and-non-goals.md) 第 1 条与第 3 条(不废除,收紧措辞)

## 背景

2026-10-12 本人提出对 `agent-runtime-min` 的新定位:

> 「彻底复刻 DeepSeek Harness,同时在 DSH 基础之上加入一些我们自己原生的、原本 DSH 靠插件实现的功能。复刻的具体含义,不是照着 DSH 抄代码,而是参考其设计,避免绕弯路;我们还是尽量要有自己的东西。可以借鉴经过市场检验的优秀共通设计,但不要完全照抄。」

这个定位与 ADR-0001 的两条现有约束存在张力,必须显式解决:

1. ADR-0001 第 1 条:只做三个机制,非目标含「不追求与 DSH 行为一致」。
2. ADR-0001 第 3 条:clean-room,读契约不抄实现。

同时,「彻底复刻」与「不要完全照抄」在字面上互斥:**要么照抄(快,但违反 clean-room 且面试叙事崩塌),要么重新推导 43 万行(远超预算)。没有停止条件的范围,等于永远到不了 L3。**

规模事实(【源码】实测):

| 项 | 量 |
|---|---|
| DSH 全仓 | 332 包 / 2,440 文件 / **430,414 LOC** |
| 运行时侧(不含 client) | **379,692 LOC** |
| 内核主干(agent/loop/session/tools/prompt/llm/持久化/沙箱/subprocess/shell) | **47,326 LOC** |
| 官方插件族(goal/jobs/schedule/workflow/todo/skill/preset/plan/ptc/subagent) | **≈37,000 LOC** |

而可用预算是设计期 8–16 小时、实现期 2027 年 1–2 月(与考研复试、春招投递重叠)。

## 决策

### 1. 「复刻」= 设计对齐,不是功能对齐

**接受**的复刻含义:

- 按 DSH 的分层设计对齐**架构**:能力接缝(definition/provider/consumer)、事件三域、日志即事实、装配与依赖方向。
- 用 DSH 的**决策记录**当路标,避免重走它已经痛过的弯路。
- 每个设计决策标注上游依据,使结论可追溯。

**不接受**的复刻含义:

- 不逐项补齐 DSH 的能力清单(那是 43 万行)。
- 不追求与 DSH 行为一致,不以其兼容性为目标。
- 不复制实现代码(clean-room 继续有效)。

**为什么**:深度来自收敛,不来自覆盖。ADR-0001 第 1 条的论证(逐项复刻必然产出「什么都有一点」的浅层 demo)在更大尺度上依然成立——只是从「13 个大类」放大到「332 个包」。

### 2. 新增范围必须通过「原生内置准入标准」

「在 DSH 之上加入我们自己原生的东西」是本项目新增的第二条主线。但**不能凭直觉加**。任何新增能力必须同时满足:

| # | 判据 | 门槛 |
|---|---|---|
| 1 | **DSH 空白度** | 优先做 DSH **没有**的能力(社区在填的空白);DSH 官方已有包的能力,内建需额外理由 |
| 2 | **JD 命中度** | 出现在 T1 岗位正文(尤其加分项逐字) |
| 3 | **可量化度** | 能变成 L3 的量化指标,否则不写进简历 |
| 4 | **同源性** | 必须能解释为「向事件日志追加正确的事件」的延伸,而不是另起一套存储 |

判据 1 的来源见 [市场实测](../market-native-builtins.md) §2:实测发现 DSH 的能力应分两类——

- **类别 A(官方已有可选插件)**:goal / plan / todo / jobs / schedule / workflow / subagent / skill / computer-use / browser-use / compaction / spill / sandbox / approval / MCP。内建它们 = 重做官方插件,面试时答不出「你和 DSH 有什么不同」。
- **类别 B(DSH 零实现,社区填坑)**:记忆系统 / 上下文洞察 / 工作树 / Docker 沙箱 / **Eval 基础设施**。内建它们 = 原创空间。

**为什么定这条**:它把「要不要内建某能力」从品味问题变成可检验的门槛。判据 4(同源性)尤其关键——它是防止项目退化成「功能堆」的唯一护栏。

### 3. 首批内建范围(按准入标准排序)

**T1 内建**(详见 [market-native-builtins.md](../market-native-builtins.md) §5):

1. **Eval 基础设施**(回归集 + Trace 评估 + LLM-as-Judge)—— 类别 B;JD 第③条整条职责;DSH 零实现;市场 4,508 个插件中仅 20 个涉及。
2. **上下文压缩 + spill** —— 已是 M2;JD 加分项逐字「上下文压缩」;量化最清晰。
3. **工具权限 + 沙箱策略** —— 已是 M3;JD 出现频率最高。

**T2 待定**:记忆系统(类别 B,但同质化严重,差异化只能来自「记忆从事件日志派生」)、持久 Goal(JD 逐字「长任务恢复」,但属类别 A,且 ADR-0001 现列为非目标)。

**T3 暂不内建**:子 Agent(17,588 LOC)、工作树、Docker 沙箱后端、电脑操作 / 浏览器(类别 A 纯复刻)、Skill 系统。

> ⚠️ **本条已被 [ADR-0003](0003-usable-harness-and-t3-scope.md) §2 作废(2026-10-12)**:范围改为**全做,不裁剪**,上述五项全部纳入。本 ADR 的 §1(设计对齐)、§2(判据)、§5(clean-room)继续有效;§3 的 T1/T2/T3 分级仅保留历史价值,不再作为范围依据。

### 4. 机制数量从 3 扩到 4,叙事主线不变

```
M1 日志即事实 ──┬─→ M2 上下文压缩      (向日志追加压缩事件)
                ├─→ M3 工具流水线      (向日志追加工具事件)
                └─→ M4 Eval 基础设施   (从日志派生证据)
```

M4 与 M1 **同源**:「从日志重建请求体」正是 eval 的输入。这不是四个独立 demo,而是**同一份日志的四种用途**——叙事主线(M1 是地基,其余都是「向日志追加正确的事件」或「从日志读出证据」)保持成立。

**降级路径相应更新**:设计期若做不完,**砍 M4,保留 M1+M2**;M3 视带宽。原 ADR-0001 第 4 条(砍 M3 保 M1+M2)被本条取代。

### 5. clean-room 边界不变,但措辞收紧

ADR-0001 第 3 条继续有效。本次收紧:

- **允许**:阅读上游 `docs/`、类型定义、README、`.agents/notes/` 决策记录,用于理解契约与设计意图。
- **允许**:借鉴经过市场检验的通用工程手法(依赖注入、生成式文档闸门、品牌类型、fail-closed 默认值)——这些不是 DSH 的专有资产。
- **不允许**:复制、改写、逐行翻译上游实现代码。
- **新增约束**:任何一份设计文档,**抽掉 DSH 的名字后仍须能独立成立**。这条是「设计对齐 ≠ 抄」的可检验形式。

## 后果

**正面**

- 「彻底复刻」有了停止条件(设计对齐,而非功能覆盖),范围重新变得可完成。
- 「加入原生功能」有了准入标准,从直觉驱动变成判据驱动。
- Eval 的引入让 M1/M2/M3 的 L3 指标**可自动产出**,把验收从手工变成基础设施。
- 面试叙事更强:不仅能讲「我读了它的契约用不同方式实现」,还能讲「我发现它缺什么、市场在填什么、我为什么选这个补」。

**负面 / 风险**

- M4 的加入使设计期预算(8–16 小时)更紧张 → 用第 4 条的降级路径兜底。
- 「Eval 排第一」的结论依赖单一 JD 样本(e签宝)→ 2027-01 需在核实春招岗位后复核排序。
- 类别 A/B 的划分基于 2026-10-12 的 DSH 快照(0.2.1-alpha.1)→ DSH 若原生补上记忆系统,类别 B 会缩小,需定期复核。
- 4,508 这个市场数字未经抽样验证 → 见 [market-native-builtins.md](../market-native-builtins.md) §6 待验证项 1。
