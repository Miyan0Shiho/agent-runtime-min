# ADR-0003:定位转为「可自用的 harness」,T3 纳入范围

- **状态**:已接受
- **日期**:2026-10-12
- **决策者**:本人
- **取代**:[ADR-0002](0002-design-alignment-and-native-builtins.md) §3 的 T3 排除条款
- **保留**:ADR-0002 §1(设计对齐)、§2(四条判据)、§5(clean-room);ADR-0001 §3

## 背景

2026-10-12 本人追加三条指示:

1. **spool 抛弃** —— 不作为参考、基座或复用来源。
2. **T3 全部纳入** —— 子 Agent / Agent Teams、工作树、Docker 沙箱、电脑操作 / 浏览器、Skill 系统,「都需要做」。
3. **本项目不再作为简历交付物** —— 目标是「先做一个能真正用的 harness」;简历项目另行落到**具体场景**中做自己的优势。

这三条与 ADR-0002 的收敛定位冲突,必须显式解决。同时,ADR-0002 §5 的 clean-room 约束(不复制实现代码)继续有效,不因范围扩大而放宽。

## 决策

### 1. 项目目标改为「可自用的 harness」

**接受**的目标:一个本人日常真的会用的 agent harness —— 能跑真实任务、能长期用、坏了能修。

**不再接受**的目标:作为简历交付物。简历项目另行立项,落到具体场景(与 [paper-overclaim-harness](../../../paper-overclaim-harness/) 的分工一致:先有 runtime,再在其上做场景)。

**为什么**:把「面试官会怎么看」从设计判据里拿掉之后,判据变成「我自己会不会用」。这是更硬、更可检验的标准,也解除了 L3 指标对简历叙事的绑定。

### 2. T3 纳入范围,ADR-0002 §3 的 T3 排除条款作废

| 能力 | DSH 同类实现 | 状态 |
|---|---|---|
| 子 Agent / Agent Teams | 17,588 LOC | 纳入 |
| 工作树 | DSH **无**;社区在填 | 纳入 |
| Docker 沙箱后端 | DSH **无**(只有 bwrap/Landlock/Seatbelt/Windows ACL) | 纳入 |
| 电脑操作 / 浏览器 | 官方 seam + 4 provider | 纳入 |
| Skill 系统 | 3,328 LOC | 纳入 |

**为什么可以纳入**:ADR-0002 排除 T3 的理由是「简历叙事稀释 + 成本」,其中「叙事稀释」随第 1 条作废而失效。成本理由依然成立,但已改由第 4 条的顺序与深度来控制,而不是由排除来控制。

### 3. ADR-0002 的四条判据降级为「排序工具」

四条判据(DSH 空白度 / JD 命中度 / 可量化度 / 与日志同源)继续用于**决定先做哪个**,但**不再用于否决**。

- **DSH 空白度**:降为参考。T3 多为类别 A(官方已有),照做,但预期是「复刻」而非「原创」。
- **JD 命中度**:**作废**。项目已与求职解耦,JD 不再是判据。
- **可量化度**:保留。指标仍是「能不能证明它真的work」的手段。
- **同源性**:保留,但放宽 —— 允许出现不由事件日志派生的子系统(如 Docker 后端、电脑操作 provider)。

### 4. 交付物与简历解耦,项目位置待定

[02-projects/README.md](../../README.md) 的定义是「能拿出去给人看的项目 = 简历项目」。本项目已不属于该定义。

**待定**:保留在 `02-projects/` 下并注明「基础项目,非简历项」,还是移出到独立位置。**本 ADR 不改动目录结构**,等范围稳定后再定。

### 5. spool 不作参考

`sources/_archive/spool/`(27,819 LOC TS,P0+P1 完成)不读、不借鉴、不复用其实现与基准集。它是「自研非 DSH 路线」的完整尝试,方向与本项目不同。

**唯一保留的价值**:作为**失败复盘材料**存在(与 [sources/README.md](../../../../sources/README.md) 的既有规则一致),不在设计期阅读。

## 后果

### 量级事实(【源码】实测,`sources/deepseek-harness/`)

纳入 T3 后,按 DSH 同类实现估算的等价规模:

| 块 | 内容 | LOC |
|---|---|---:|
| 内核主干 | agent / agent-loop / session / tools / system-prompt / llm / projection | 25,713 |
| T1+T2 | compaction / spill / sandbox / interaction / goal / persistence-jsonl | 24,122 |
| T3 | subagent / agent-team / skill / browser-use* / computer-use* | 22,912 |
| **小计** | | **72,747** |
| 「能真正用」还必需但未计 | fs / shell / subprocess / lsp / web / mcp | 32,538 |
| **合计** | | **≈105,285** |

参考:D SH 全仓 430,414 LOC / 332 包。

**这是等价规模,不是我们的目标 LOC。** 自研会更小(去掉产品化开销:client 139,016 行、experimental 49,353 行、api 20,627 行、extensions 21,734 行都不需要)。**⚠️ 本 ADR 初稿据此外推出「以年计」,已被 §7 推翻——见那里的校准证据。**

**正面**

- 目标判据从「面试官怎么看」换成「我会不会用」,更硬。
- T3 纳入后能力面完整,不再需要为「为什么不做 X」辩护。
- 与 paper-overclaim-harness 的分工清晰:先 runtime,后场景。

**负面 / 风险**

1. **「能真正用」与「从零自研」存在张力。** DSH 本身已经是一个能真正用的 harness(MIT、本机已装、319 包已构建)。从零重写意味着在过渡期里,手上能用的仍是 DSH。
2. ~~量级 ≈10 万 LOC,收口周期以年计。~~ **已作废,见 §7**(产出速度按 `spool` 校准为以周计)。
3. **范围失控风险回到最高。** ADR-0001 把「范围失控」列为项目最大风险,当时用「只做三个机制」来防;现在护栏已全部撤除,需要新的护栏(见 §6.2 待决项 5)。
4. **简历解耦后,「L3 指标」失去外部意义。** 需重新定义「能用」的验收。原裁断 2(行为判据)已按 §6.3 撤回,不再作为判据。
5. **真正的瓶颈是「质」不是「量」**——见 §7.3。

### 6.3 「日常用它」撤回为判据,范围改为全做(2026-10-12 本人指正)

**本人指正**:

> 「日常用它只是一个说法,你不知道用户日常需要用到哪些内容,所以,全做。」

**我错在哪**:我把「日常真的用它」当成了一道**准入闸门**——用它否决能力(例如 T3 顺序稿的 §2.1「使用判据」、§2.3「两周没被日常使用就删」)。但我**不知道本人日常需要用到什么**,所以这道闸门无法被任何人正确执行:它会随机地砍掉本人真正需要的能力,只因为我看不到那个需求。

**修正后的理解**:

| 项 | 修正前(错) | 修正后 |
|---|---|---|
| 「日常用它」的性质 | 准入判据,用于否决 | **方向性说法**,表达「要真能用、不是玩具」的意图 |
| 能力范围 | 按判据裁剪 | **全做**。DSH 有的、社区在填的,都做 |
| 谁能判断「需不需要」 | 我(根据我的可见信息) | **只有本人**,且是在**用过之后** |
| 删除的依据 | 我的猜测(「没被日常使用」) | **本人的实际使用反馈** |

**直接后果**:

1. **`t3-ordering-and-guardrails.md` §2 的护栏建议作废** —— 其中「使用判据」和「允许删除」两条都建立在我无法执行的判断上。
2. **顺序仍然需要**(见 §1 的依赖拓扑):「全做」回答的是**范围**,不回答**先后**。22 条依赖的 `subagent` 依然不可能先于它的前置跑起来。
3. **真正的护栏只剩「顺序」与「垂直切片」**:不裁剪能力,但一次只推进一步,且每步端到端可用。

### 6.4 顺序与执行护栏(2026-10-12)

范围全做之后,保留的护栏**只有「怎么做」类**,不含「该不该做」类(后者见 §6.3):

| # | 护栏 | 内容 |
|---|---|---|
| 1 | **依赖拓扑** | 前置能力必须先**能用**,才开下一个。实测 `subagent` 依赖 22 个包,物理上不可能先跑 |
| 2 | **垂直切片** | 每个能力推进到端到端可用再开下一个;只能当 stub 的不许进 |
| 3 | **一次一个** | 任一时刻只有一个能力处于「正在做」 |
| 4 | **设计期不实现** | 见裁断 9 —— 记录完即停,不动手 |

**当前起点**:内核主干 M1–M4(裁断 8)。T3 顺序见 [t3-ordering-and-guardrails.md](../t3-ordering-and-guardrails.md) §1。

## 7. 关于「以年计」的修正(2026-10-12 本人指正)

### 7.1 我之前错在哪

本节初稿把 DSH 的**等价 LOC** 当成了自研的**工作量**,并默认由人逐行手写,据此得出「以年计」。这个推断有两处错误:

1. **把「等价规模」当「工作量」。** DSH 的 41 万行非测试代码里,含大量产品化开销:client 139,016 行(界面)、experimental 49,353 行、api 20,627 行、extensions 21,734 行。这些是**它的产品形态的成本**,不是「一个能用的 harness」的必要成本。
2. **假设由人手写。** 实际是 agent 辅助开发,产出速度不在同一量级。

### 7.2 校准证据:`spool` 的实测速度

`spool`(同工作区、可复核)给出了直接标定:

| 项 | 值 |
|---|---|
| 自研代码 | **27,819 行** TypeScript(`src/`,57 文件,不含测试) |
| 首末提交间隔 | **31.4 小时**(2026-09-19 16:52 → 2026-09-21 00:13) |
| 完成度 | P0 + P1(Goal/编排/Plan/worktree/sandbox/JSON-RPC/SDK/ACP/MCP/hooks/Web/Electron 薄壳) |

按此校准,**≈10 万行等价规模是以周计,不是以年计**。本人判断正确。

> 注意这个证据的**边界**:它证明的是**产出速度**,不是**成功**——`spool` 仍被归档(见 §7.3)。但它足以推翻「以年计」。

### 7.3 修正后的风险判断:瓶颈从「量」转到「质」

既然产出速度不是约束,真正的瓶颈变成:

| 维度 | 说明 |
|---|---|
| **能不能真的用** | 代码写完 ≠ 敢用它改自己的仓库。这是**方向性要求**,不是可执行的准入判据(见 §6.3) |
| **可靠性** | 上下文压缩失真、工具失败恢复、会话损坏 —— 这些是「能用」与「不能用」的分界,不是功能数量问题 |
| **clean-room 的重推导成本** | 不抄源码意味着每个机制要自己推一遍。选 Python 后与上游生态脱钩,这一步无法回避 |
| **收敛** | 快速产出大量代码之后,把它收敛成一个**连贯的**系统,比写出来更难 |

**结论**:「以年计」的悲观判断作废;但风险并未消失,只是换了形态——**从「做不完」变成「做出来了但不可靠/不连贯」**。`spool` 的归档原因(主线文档未记录)很可能属于后者。

### 7.4 对原 §7.3 建议的影响

原建议(「找一个窄场景先做到日常可用」)从**必要缓解措施**降级为**可选排序策略**:

- 若产出速度确实以周计,则「先做完整内核再谈使用」是可行的,不必强行收窄。
- 但「窄场景先跑通」仍有独立价值:它让裁断 2 的判据(日常真用)尽早可满足,反馈回路尽早闭合。

**因此保留为建议,不作为约束。** 是否采用由本人按实际推进节奏裁断。
